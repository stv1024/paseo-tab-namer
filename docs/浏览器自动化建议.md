# 浏览器自动化建议

本文供涉及浏览器自动化的项目参考。没有此类测试需求时，无需安装浏览器或引入启动工具。项目可根据目标平台、浏览器兼容性和实测结果调整做法。

## 按运行平台选择

这里的平台指运行测试进程的操作系统；例如，在 Windows 上模拟 iPhone 视口，仍属于 Windows 测试环境。

| 运行平台 | 通常建议 | 适用范围 |
| --- | --- | --- |
| Windows | 无头 Chromium 测试可优先评估与 Playwright 版本配套的 Chrome Headless Shell。需要完整 Chrome 时按用途选择并验证。 | 部分完整 Chrome 版本在新配置初始化时检查 Windows 空密码，频繁启动可能累计登录失败并锁定账户。完整 Chrome 的无头模式仍可能触发这条链路。 |
| macOS / Linux | 可按测试需求选择 Headless Shell、完整 Chrome、WebKit 或其他浏览器，保留适合项目的现有方案。 | 不适用上述 Windows 认证链路，无需仅为该问题迁移到 Shell、复用持久配置或增加 Windows 登录事件检查。 |

这一 Windows 判断来自 2026-11-01 的本机对照实验：系统 Chrome 155 与完整 Chrome for Testing 156 出现账户验证失败，Headless Shell 未出现对应事件。证据不代表所有浏览器版本的行为，也不代表 macOS/Linux 已完成兼容性测试。上游版本更新后，可按实际结果调整。

## 通用的测试习惯

通常建议复用项目已有的浏览器启动入口，集中处理版本、参数和进程清理。测试结束后关闭浏览器；需要数据隔离时使用独立 BrowserContext。只有选择复用持久配置时，才需要处理共享配置的并发访问和数据保留。

GPU 参数按运行平台选择。D3D11 适用于 Windows；macOS/Linux 按实际后端配置。性能测试可核对实际 renderer。截图、媒体、扩展和浏览器行为按项目需要验证，页面视口模拟不等于目标设备的真实浏览器验收。

## 可选的启动工具

可参考 [IT 助理仓库的 browser-launcher](https://github.com/stv1024/my-assistant-team/tree/main/tools/browser-launcher)。模板只提供建议文档，不自动安装依赖或复制工具；已有合适入口时，可继续使用。

采用参考实现时，通常可按以下步骤接入：

1. 将参考实现 `launch-browser.mjs` 放入项目的 `tools/lib/`，根据项目现有依赖安排 `playwright-core`，无需仅为接入而升级版本。
2. 在项目目录用对应 Playwright CLI 安装所需浏览器。Shell 的命令是 `node node_modules/playwright-core/cli.js install chromium --only-shell`，可按项目习惯加入 `browsers:install` 脚本。
3. 将相关测试入口接入工具，并验证页面、媒体或 GPU 等实际使用能力。Windows 上排查本问题时，可按测试 PID 和时间窗口核对 Security 4625/4740；macOS/Linux 无需执行这项 Windows 检查。

参考实现的 `launchBrowser()` 在各平台都默认使用 Headless Shell，这是共享实现的默认值。macOS/Linux 项目可采用完整 Chrome 入口，或调整项目本地实现；无需把 Shell 当作平台安全要求。

`launchFullChrome({ profile: 'project-ui', headed: true })` 返回 `{ context, close }`，使用专用持久配置和并发锁。这个配置策略可按项目需要采用；在受影响的 Windows 环境中，首次初始化或密码变更后仍可能触发账户验证，不能据此保证不会锁定。具体 API、清理方式和限制见参考实现说明。

项目采用其他方案时，可简要记录原因和验证结果，便于后续维护；无需保持工具副本与参考实现逐字一致。
